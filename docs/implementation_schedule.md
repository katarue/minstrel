\## 0. このドキュメントについて



Minstrelプロジェクトの実装手順を時系列で示すスケジュール表である。



計画書本体（minstrel\_project\_plan.md）で定義した戦略・設計・哲学を、実際にどの順番でどう実装していくかを定める。



実装はすべてClaude Codeに指示する形で進める。ムーチョさんは意思決定とディレクションに専念し、コードは書かない。

\## 7. フェーズ5：運用・改善（継続）



\### 目的

\*\*MVPを「壊れない仕組み」に育て、改善を続ける。\*\*



\### 定期タスク



| 頻度 | タスク |

|------|-------|

| 毎日 | Prefectフロー実行ログの確認（自動通知ベース） |

| 毎週 | 自動公開された新着イベントの抽出スポットチェック（5〜10件） |

| 毎月 | API消費量・コストレビュー |

| 毎月 | 機械検証ルールの精度評価・調整 |

| 四半期 | サイト全体のUX見直し |



\### 改善の優先順位



1\. 機械検証で「保留」になった割合が高い場合 → ルール調整

2\. 中止・延期の検知漏れがあった場合 → キーワード追加

3\. ユーザーからのフィードバック → 機能追加検討

4\. アフィリエイト承認 → 各販売サイトへのリンク強化

\## 9. クリティカルパス



プロジェクト全体で最も重要な依存関係は以下。



```

DB設計（1-A） 

&#x20;   ↓

Next.js基盤（1-B）+ スクレイピング基盤（2-A）+ X検索基盤（2-B）

&#x20;   ↓

基本ページ実装（1-C）+ Claude API構造化（2-C）

&#x20;   ↓

仮公開（1-D）+ 機械検証（2-D）

&#x20;   ↓

画像処理（2-E）

&#x20;   ↓

Prefect統合（2-F）← ここが最重要のボトルネック

&#x20;   ↓

機能拡充（フェーズ3）

&#x20;   ↓

過去データ投入＋本公開（フェーズ4）

```



最も時間がかかり、トラブルが起きやすいのは\*\*フェーズ2-F（Prefect統合）\*\*。すべての要素が組み合わさるため、ここで詰まる可能性が高い。

\## 10. リスク管理



\### 想定されるリスクと対応



| リスク | 確率 | 影響度 | 対応 |

|--------|------|--------|------|

| スクレイピング対象サイトの構造変更 | 中 | 中 | 失敗通知で即対応、AランクからB降格も可 |

| Claude API出力の不安定 | 中 | 高 | リトライロジック＋スキーマ厳密化 |

| twitterapi.ioのサービス停止 | 低 | 高 | X検索を補助扱いにし、Aランク情報源を主軸 |

| 自宅PC障害 | 中 | 中 | 通知で気づける体制、最悪は数日停止を許容 |

| 著作権関連のクレーム | 低 | 高 | 削除導線を最初から用意、ホットリンク禁止徹底 |

| 月額コスト超過 | 低 | 低 | フェーズ2でコスト計測、必要なら頻度調整 |

\## 11. 進捗管理



\### Notion管理



進捗は計画書と同じ「Webサービス企画」ページ配下にタスク管理ページを作って運用する想定。



各フェーズの完了時にチェックを入れる。



\### Claude Codeへの指示単位



各タスク（1-A-1等）を単位として、Claude Codeに依頼する形が望ましい。一度に大きすぎる粒度を投げると、品質が落ちる。



例：

> 「Minstrelプロジェクトの1-A-1を実装してください。SupabaseでDBスキーマを設計し、events、organizers、game\_titles、event\_game\_titlesのCREATE TABLE文を作成してください。詳細は計画書の5章を参照してください。」
